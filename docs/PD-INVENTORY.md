# Перечень данных, которые хранит и обрабатывает портал hr.admsr.ru

Документ для ответственного за организацию обработки ПД и за защиту информации (152-ФЗ, ПП №1119, приказ ФСТЭК №117).
Составлен по состоянию кода на 07.10.2026 (ветка `round-buttons`), обновлён после закрытия `/media/`, удаления форм о коррупции и ввода журнала доступа (миграция 0058). Это техническая выписка из кода, а не юридическое заключение:
цели, правовые основания и сроки хранения нужно подтвердить на стороне администрации. Пункты «Уточнить» требуют ответа от эксплуатации.

## 1. Общая схема

| Элемент | Как устроено |
|---|---|
| Фронтенд | Nuxt 4, статика за nginx (`hr.admsr.ru`), отдельная сборка для киоска (`kiosk-hr.admsr.ru`, без форм) |
| Бэкенд | Django REST, `backend/DjangoProj`, админка `/admin/` (в киоске закрыта: nginx отдаёт 404) |
| База данных | SQLite (`db.sqlite3`) по умолчанию; MySQL, если задан `DATABASE_URL` или используется `prod_settings.py` |
| Файлы | `backend/DjangoProj/media/` на диске сервера; публичные каталоги отдаются по `/media/…`, каталоги с ПД только вошедшим сотрудникам с правом просмотра заявок (`api/media.py`) |
| Почта | SMTP (если задан `EMAIL_HOST`); копии заявок уходят получателям из справочника `ApplicationRecipient` |
| Аналитика | Яндекс.Метрика (`mc.yandex.ru`), включается только после согласия на cookie |
| Доступ к данным | Django-админка: суперпользователи и группа «Модератор» (все права приложения `api`, кроме журнала доступа к ПД) |

## 2. Данные граждан (персональные данные)

| Источник (форма на сайте) | Таблица / файлы | Состав данных | Согласие | Рассылка копии на почту |
|---|---|---|---|---|
| Отклик на вакансию и в кадровый резерв | `JobApplication`; `media/resumes/`, `media/photos/` | Фамилия, имя, отчество, дата рождения, телефон, email, **адрес регистрации и проживания**, гражданство, образование, специальность, стаж, трудовая деятельность, **семейное положение, наличие детей**, фото, резюме (pdf/doc/docx), источник информации о вакансии | 4 флага (ложные сведения, проверка, ПД 152-ФЗ, пересылка в поселения), проверяются и на сервере | Да, с вложениями (до 20 МБ) |
| Подписка на вакансии (с необязательным резюме) | `VacancySubscription`; `media/subscription_resumes/` | Имя, email, телефон, желаемая должность, образование, опыт, «о себе», файл резюме, выбранный орган | Чекбокс только на фронтенде, **на сервере и в БД не хранится** | Да, если приложено резюме или заполнены поля резюме |
| Заявка на практику | `PracticeApplication`; `media/practice_applications/` | ФИО, дата рождения, телефон, email, вуз, курс, специальность, период практики, комментарий, сопроводительное письмо | Флаг в БД, проверяется на сервере | Да |
| Обратная связь | `Feedback`; `media/feedback_photos/` | Текст и фото (прямых идентификаторов нет, но граждане могут указать их в тексте) | **Нет** | Да |
| Предложение по обучению | `TrainingFeedback` | Имя (необязательно), подразделение, текст | **Нет** | Да |

Дополнительно по подпискам: токен отписки подписан `SECRET_KEY` и содержит email; письма о новых вакансиях уходят всем активным подписчикам.

## 3. Данные должностных лиц и сотрудников (публикуются на сайте)

Нужно подтвердить основание для публикации: согласие работников на распространение (ст. 10.1 152-ФЗ) или иное основание. Для лиц на кадровом резерве и победителей конкурсов это особенно важно.

## 4. Служебные данные пользователей админки

| Что | Где |
|---|---|
| Логины, ФИО, email, хэши паролей сотрудников | `auth_user` |
| Журнал действий в админке (кто и что менял) | `django_admin_log` |
| **Журнал доступа к ПД**: просмотр, изменение, скачивание файлов, получение с сайта, передача по почте, входы | `PersonalDataAccessLog`, в админке «Журнал → Журнал доступа к ПД» (только чтение, только суперпользователь) |
| Сессии | `django_session` |
| Получатели заявок: ФИО и email уполномоченных лиц | `ApplicationRecipient` |

## 5. Технические данные посетителей

| Что | Где и как |
|---|---|
| IP-адреса, User-Agent, URL запросов | Журналы nginx и WSGI-сервера (Django не пишет собственный `LOGGING`). **Уточнить:** срок хранения и кто имеет доступ |
| Cookie `corruption_cooldown`, `feedback_cooldown`, `training_feedback_cooldown` | Технические, живут 60 секунд, HttpOnly |
| Cookie сессии и CSRF | Для админки |
| Выбор по cookie-баннеру | Хранится в браузере |
| Яндекс.Метрика (`_ym*`, при согласии — Вебвизор и карта кликов) | Передаётся в Яндекс, на сервере портала не хранится; после отказа cookie удаляются |

## 7. Замечания по результатам проверки кода

### Устранено

1. **Файлы с ПД закрыты.** `/media/` отдаёт каталоги `resumes`, `photos`, `subscription_resumes`, `practice_applications`, `feedback_photos` только сотрудникам, вошедшим в админку и имеющим право просмотра соответствующих заявок; для остальных 404 (не вошёл) или 403 (нет права). Публичны только каталоги сайта (`tenders`, `staff`, `partners`, `anti_corruption_docs`, `competitions`, `staff_reserve`, `vacancies`, `departments`, `news`). Любой новый каталог закрыт по умолчанию (доступ только суперпользователю). Каждое скачивание пишется в журнал.
2. **Формы о коррупции удалены** вместе с моделью, API (`/api/submit-corruption-report/`), админкой и файлами. На странице «Нет коррупции!» остаётся баннер «Госуслуги. Решаем вместе» (платформа обратной связи).
3. **Журнал доступа к ПД введён** (`api/audit.py`, модель `PersonalDataAccessLog`), см. раздел 9.
4. **Локальные данные убраны из индекса git:** `backend/DjangoProj/db.sqlite3`, `frontend/.data/`, `media/resumes/` и остальные каталоги загрузок из форм добавлены в `.gitignore`.

### Остаётся

1. **Нет согласия** на формах обратной связи и предложения по обучению (в БД и на сервере согласие не хранится). В форме подписки согласие есть только на фронтенде.
2. **Избыточность анкеты `JobApplication`**: адрес регистрации и проживания, семейное положение, дети, фото. Принцип минимизации (ст. 5 152-ФЗ) на этапе отклика вряд ли это оправдывает.
3. **Нет автоматического удаления.** Сроки хранения заявок, подписок и журнала в коде не заданы. Нужны регламент и процедура уничтожения.
4. **Политика конфиденциальности** (`frontend/app/data/privacy-policy.ts`): не перечислены обработчики и получатели (почтовый сервер, Яндекс), нет разделения по формам. Пункт 8.2 («никогда не будут переданы третьим лицам») противоречит передаче в Яндекс и рассылке копий заявок.
5. **История git всё ещё содержит удалённые файлы:** прежние версии `db.sqlite3` (17 коммитов), `media/resumes/` и `media/corruption_reports/`. Если в них когда-либо были реальные данные, нужна чистка истории (`git filter-repo`) с принудительной публикацией и сменой секретов. Это отдельное решение.
6. **Секреты в репозитории.** `DjangoProj/prod_settings.py` под контролем версий и содержит параметры подключения к MySQL на pythonanywhere.com, включая пароль. Если файл когда-либо использовался в бою, пароль нужно сменить; если это наследие, файл удалить из репозитория. `SECRET_KEY` имеет небезопасное значение по умолчанию (есть только предупреждение при `DEBUG=False`).
7. **Размещение.** Нужно подтвердить, что боевая БД и файлы находятся на территории РФ (ст. 18 ч. 5 152-ФЗ). Упоминание зарубежного хостинга в `prod_settings.py` и `ALLOWED_HOSTS` (`.onrender.com`) нужно закрыть явным ответом, что они не используются.
8. **Контроль доступа.** Группа «Модератор» получает все права приложения `api`, то есть доступ ко всем заявкам. Матрицы «кто видит анкеты, а кто только публикует новости» нет.
9. **Деплой сценария B.** Режим `pack_deploy.py` с архивами БД и `media/` упаковывает всю `media/`, включая каталоги с ПД. Допустим только для переноса тестовых данных.
10. **Проверка на сервере.** Закрытие `/media/` работает, пока nginx проксирует `/media/` в Django (так в `deploy/nginx-kiosk.conf`). Если на боевом сервере задан `alias` на каталог `media/`, nginx будет отдавать файлы напрямую в обход проверки.

## 8. Что нужно уточнить у эксплуатации

- Где физически размещены сервер, БД, `media/` и почтовый сервер, кто их администрирует (своя инфраструктура, ЦОД, хостинг).
- Кто имеет доступ в админку и в каком количестве (список `auth_user`).
- Срок хранения и ротация журналов nginx.
- Резервное копирование: где лежат копии БД и `media/`, как долго, кто имеет доступ.
- Включён ли HTTPS на всех доменах и заданы ли `DJANGO_HTTPS_ONLY=True` и собственный `DJANGO_SECRET_KEY` на боевом сервере.
- Подавалось ли уведомление в Роскомнадзор об обработке ПД и какие цели и категории в нём указаны.
- Утверждены ли приказом: перечень ИСПДн, уровень защищённости, ответственный за ЗИ, регламент уничтожения ПД.

## 9. Журнал доступа к ПД: что фиксируется

| Событие | Когда | Что пишется |
|---|---|---|
| Просмотр списка | Открыт список заявок, подписок, обратной связи, получателей заявок | Раздел, имена параметров поиска и фильтров (значения не пишутся) |
| Просмотр записи | Открыта карточка записи | Раздел, номер записи |
| Создание, изменение, удаление | Действия в админке | Раздел, номер записи |
| Скачивание файла | Открыт файл из закрытого каталога `/media/` | Каталог, путь к файлу (имя файла может содержать ФИО) |
| Получено с сайта | Отправлена форма отклика, подписки, практики, обратной связи, предложения по обучению | Раздел, номер записи, IP |
| Передача по почте | Копия заявки ушла получателям | Раздел, номер записи, число получателей и вложений |
| Вход, выход, неудачный вход | Админка | Логин, IP |

В каждой записи также время, пользователь (если вошёл), IP (за nginx берётся из `X-Real-IP`, только если запрос пришёл с самого сервера) и User-Agent.
Журнал виден только суперпользователям и только для чтения. Срок хранения журнала и порядок его архивирования нужно утвердить: автоматической очистки нет.
